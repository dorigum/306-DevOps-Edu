```java
		<array>
			<value>classpath:info.properties</value> 
			<value>classpath:db.properties</value>
		</array>
	</property>
</bean>
```

```java
@Bean // XML의 위에 태그와 동일
public PropertyPlacehoderConfigurer getPropertyPlaceholderConfigurer() {

}
```

	- **환경 설정을 돕는 클래스 위에 선언(생성)**

```java

		PropertyPlacehoderConfigurer p = new PropertyPlacehoderConfigurer();
		p.setLocation(리소스배열);

}
```

# Java 16 record란?

## 1. record란 무엇인가?
`record`는 **Java 16**부터 정식 도입된 데이터 전용 클래스(Data Carrier Class)이다.
즉, **불변(immutable)한 데이터 객체**를 간단하게 정의하기 위해 만들어진 새로운 클래스 타입이다.

> ✅ 요약
> **`record`** = **불변 데이터를 담는 간결한 클래스 문법**

---
## 2. 왜 필요한가?

기존의 **DTO (Data Transfer Object)** 나 **Value Object**를 만들 때, 아래처럼 **보일러플레이트 코드(boilerplate code)** 가 너무 많았다.

```java
public class Person {
    private final String name;
    private final int age;

    public Person(String name, int age) { // 생성자
        this.name = name;
        this.age = age;
    }

    public String getName() { return name; } // getter
    public int getAge() { return age; }

    @Override
    public String toString() { // toString
        return "Person{name='" + name + "', age=" + age + "}";
    }

    @Override
    public boolean equals(Object o) { ... } // equals
    
    @Override
    public int hashCode() { ... } // hashCode
}
```

이런 단순 데이터 클래스임에도 불구하고 **생성자, getter, equals, hashCode, toString**을 일일이 작성해야 했다.

➡️ 그래서 이런 중복 코드를 줄이기 위해 **record가 등장**했다.

---
## 3. record의 기본 문법

```java
public record Person(String name, int age) { }
```

이 한 줄로 위의 긴 클래스를 완전히 대체할 수 있다.

자동으로 다음 메서드들이 생성된다. 👇
- `private final` 필드
- `public` 생성자
- `getter` (`name()` / `age()`)
- `equals()` / `hashCode()`
- `toString()`

---
## 4. 특징 요약
|항목|설명|
|---|---|
|**불변성(Immutable)**|모든 필드는 `final`이며, 값 변경 불가 , ==**setter 없음**==|
|**자동 생성 메서드**|생성자, 접근자, equals, hashCode, toString 자동 생성|
|**클래스 상속 불가**|`record`는 `final`이라 상속 불가능|
|**Interface 구현 가능**|인터페이스는 구현 가능|
|**간결함**|DTO, VO, 이벤트 객체 등에 매우 적합|

---
## 5. 간단한 예제

```java
public record Product(String name, double price) { }

public class RecordExample {
    public static void main(String[] args) {
        Product p1 = new Product("Laptop", 1200.00);
        
        System.out.println(p1.name()); // "Laptop"
        System.out.println(p1.price()); // 1200.0
        System.out.println(p1); // Product[name=Laptop, price=1200.0]
        
        // 불변성 확인
        // p1.price = 999.0; // ❌ 컴파일 에러
    }
}
```


---
## 6. Custom 생성자와 메서드 정의도 가능

record도 **추가 로직이 필요한 생성자나 메서드**를 정의할 수 있다.

```java
public record User(String name, int age) {
    //아래 성생자는 모든 필드를 인자로 받는 기본 생성자에 사용자 정의 로직을 추가한 형태
    public User { 
        if (age < 0) throw new IllegalArgumentException("나이는 음수가 될 수 없습니다.");
    }

    public String greeting() {
        return "안녕하세요, " + name + "님!";
    }
}
```

**주의 : 위 코드를 보면 record 첫줄이 괄호가 있고, 생성자 정의 옆에 괄호 없다!
(클래스 선언과 다름)**

---
## 7. 언제 사용하는가?
|상황|record 적합 여부|
|---|---|
|단순히 데이터 전달용 클래스 (DTO)|✅ 매우 적합|
|값 객체(Value Object) ( Money, Point 등)|✅ 매우 적합|
|엔티티(Entity, JPA 등 변경 가능한 객체)|❌ 부적합 (불변이기 때문)|
|서비스 로직이 많은 클래스|❌ 부적합|

---
## 8. 비교: `record` vs `class` vs `@Data` (Lombok)

|항목|record|일반 class|Lombok @Data|
|---|---|---|---|
|코드 간결성|✅ 최고|❌ 많음|✅ 간결함|
|불변성|✅ 기본 불변|❌ 수동 설정 필요|❌ mutable 기본|
|상속|❌ 불가|✅ 가능|✅ 가능|
|JDK 지원|✅ 표준|✅ 표준|❌ 외부 라이브러리|

---

## 9. 정리
## Java `record`의 주요 장점 요약

|구분|설명|
|---|---|
|**보일러플레이트 코드 제거**|생성자, getter, `equals()`, `hashCode()`, `toString()`을 자동 생성하여 코드량을 크게 줄임|
|**불변(Immutable) 객체 제공**|모든 필드가 `final`이라 값이 변경되지 않아, 스레드 안전(thread-safe)하고 안정적임|
|**의도 명확성**|"**이 클래스는 데이터 전달용**"임을 명확하게 표현할 수 있어 코드 가독성 향상|
|**표준 문법 (Lombok 대체)**|`@Data`, `@Value` 같은 Lombok 의존 없이 JDK 표준 문법으로 동일한 기능 제공|
|**간결하고 유지보수 용이**|데이터 중심 클래스(DTO, VO, Response 등)에 최적 — 작성과 유지보수가 단순해짐|

✅ `record`는 **불변 데이터 객체를 간결하고 안전하게 정의할 수 있는 Java 표준 문법**이다.

---
## 10. `record`와 JPA(Entity) 사용 시 충돌 이슈 및 주의점

`record`는 **불변(immutable)** 데이터를 표현하기 위해 만들어진 문법이지만, **JPA Entity**는 **가변(mutable)** 객체를 전제로 동작한다.

> 즉, **record는 불변 객체용**,
> **JPA Entity는 가변 객체용** 이라는 철학적 차이가 있음.

이 둘을 함께 사용할 경우 여러 가지 **런타임 문제**와 **설계 불일치**가 발생할 수 있다.

---
## JPA Entity의 기본 전제
JPA의 Entity는 다음과 같은 특성을 전제로 설계되어 있다.

| 항목                     | 설명                                          |
| ---------------------- | ------------------------------------------- |
| **기본 생성자 필수**          | JPA가 리플렉션으로 객체를 생성하므로 기본 생성자 필요             |
| **Setter 또는 필드 접근 가능** | DB 조회 후 값을 채워 넣기 위해 필드에 접근해야 함              |
| **가변 객체(mutable)**     | 조회된 후 변경이 가능해야 함 (`@Transactional` 내 변경 감지) |
| **프록시 생성 가능**          | Lazy Loading 시 프록시 객체로 대체 가능해야 함            |
➡️ 즉, **JPA는 내부적으로 객체의 상태를 변경하거나 프록시를 대체하는 구조**이기 때문에

`final` 필드와 불변 객체를 사용하는 `record`와는 충돌이 발생한다.

---
## 🔷 3. record의 제약사항

|항목|record의 특징|JPA에서 문제 발생|
|---|---|---|
|**모든 필드 `final`**|값 변경 불가|엔티티의 변경 감지(dirty checking) 불가능|
|**기본 생성자 없음**|명시적 생성자 필요|JPA가 리플렉션으로 생성 불가|
|**상속 불가 (`final`)**|상속 구조 사용 불가|프록시 생성 불가 (Lazy Loading 불가)|
|**불변 객체**|setter 없음|DB → 객체 매핑 후 수정 불가능|

➡️ 결국, JPA에서 `record`를 **엔티티로 직접 사용하는 것은 권장되지 않는다.**

# AOP
## AOP란?
**AOP (Aspect-Oriented Programming, 관점 지향 프로그래밍)** 은 핵심 비즈니스 로직과 부가적인 관심사(예: 로깅, 보안, 트랜잭션)를 분리하여 코드의 **관심사 분리(Separation of Concerns)** 를 실현하는 프로그래밍 패러다임이다.

## 핵심 용어 정리

### 1. **Target (대상 객체)**

- **정의** : AOP 기능이 적용될 **원래의 비즈니스 객체**
- **필요성** : 핵심 로직(예: 회원가입, 결제처리)을 포함하고 있음.
- **언제?** : 모든 AOP가 적용되는 대상은 이 Target임.

```java
public class MemberService {
    public void join(String name) {
        System.out.println(name + " 가입 완료");
    }
}
```

---

### 2. **JoinPoint (조인 포인트)**

- **정의** : AOP를 적용할 수 있는 **지점**. Spring AOP에서는 **메서드 실행 시점**만 **JoinPoint이다.**
- **필요성** : **"어디"에** 부가 기능을 넣을 지를 지정하기 위한 개념.
- **언제?** : 메서드 호출 시 (Before, After, Around 등)

```java
@Before("execution(* com.example..*(..))")
public void logBefore(JoinPoint joinPoint) {
    System.out.println("호출 메서드: " + joinPoint.getSignature());
}
```


---
### 3. **Pointcut (포인트컷)**
- **정의** : JoinPoint 중에서 AOP를 적용할 **정확한 위치를 필터링**하는 표현식.
- **필요성** : 모든 메서드에 AOP를 걸지 않고, 필요한 메서드에만 적용하기 위해.
- **언제?** : Advice를 적용할 메서드를 **선택**할 때 사용.

```java
@Pointcut("execution(* com.example.service..*(..))")
public void serviceMethods() {}
```

- **execution의 예**
 ![[Pasted image 20260508141616.png]]

---
### 4. **Advice (어드바이스)**

- **정의** : 실제로 실행되는 **부가 기능 로직**
- **종류** :
    - `@Before`: 메서드 실행 전
    - `@After`: 메서드 실행 후 (예외 여부 무관)
    - `@AfterReturning`: 정상 실행 후
    - `@AfterThrowing`: 예외 발생 후
    - `@Around`: 전/후 모두 제어

```java
@Before("serviceMethods()")
public void beforeAdvice() {
    System.out.println("서비스 호출 전 로깅");
}
```

---

### 5. **Advisor (어드바이저)**

- **정의** : **Pointcut + Advice** 를 묶어 놓은 Spring 내부 객체.
- **필요성** : Spring AOP는 이 객체를 기준으로 프록시를 생성함.
- **언제?** : 내부적으로 AOP 적용 대상 객체 생성 시 사용됨 (직접 선언은 드묾).

```
Advisor = Pointcut + Advice
```

---

### 6. **AOP Proxy (AOP 프록시 객체)**

- **정의** : Spring이 만든 **프록시 객체**로, 실제 대상(Target)을 감싸고 AOP 기능을 제공함.
- **종류**:
    - JDK Dynamic Proxy (인터페이스 기반)
    - CGLIB(Code Generation Library) Proxy (클래스 기반)
- **언제?** : ApplicationContext가 실행될 때 빈으로 등록된 대상에 AOP 설정이 있으면 Proxy로 감싸 생성됨.

[JDK Dynamic Proxy vs CGLIB](https://www.notion.so/JDK-Dynamic-Proxy-vs-CGLIB-357a7a6c42ce808789fcf1cec40409f9?pvs=21)

---

### 7. **Weaving (위빙)**

- **정의** : **Advice를 실제 코드에 적용하는 과정**.
- **종류** :
    - Compile-time
    - Load-time
    - **Runtime (Spring AOP 방식)**

```
Weaving = JoinPoint에 Advice를 엮는 작업
```

### 2. 서비스 클래스

```java
@Service
public class OrderService {

        System.out.println("주문 처리: " + item);
    }
}
```


---
### 3. AOP 설정 클래스

```java
@Aspect
@Component
public class LoggingAspect {

    @Pointcut("execution(* com.example.demo.service..*(..))")
    public void serviceLayer() {}

    @Before("serviceLayer()")
    public void logBefore(JoinPoint joinPoint) {
        System.out.println("실행 전: " + joinPoint.getSignature());
    }

    @AfterReturning("serviceLayer()")
    public void logAfter() {
        System.out.println("실행 완료!");
    }
}

```

## 🧠 정리

- **AOP는 관심사의 분리**를 통해 로직을 깔끔히 나누는 강력한 기법이다.
- 이 개념은 Spring Security, Logging, Transaction과 같은 다양한 곳에 쓰여진다.
- 실무에서는 `@Aspect`, `@Before`, `@Around` 등으로 사용하는 경우가 많으며, 내부적으로는 Proxy와 Advisor 개념이 작동한다.

Spring AOP에서 사용하는 프록시 기법에는 두 가지가 있다. 바로 **JDK Dynamic Proxy**와 **CGLIB Proxy이다**. 이 둘은 AOP의 핵심 구현 메커니즘으로, **프록시 객체(AOP Proxy)** 를 만들어서 부가 기능(Advice)을 주입한다.

## ✅ 1. JDK Dynamic Proxy

### 📌 개념

- **Java의 기본 Proxy 클래스 (`java.lang.reflect.Proxy`)를 사용**하여 인터페이스 기반으로 프록시를 생성한다.
- Target 객체가 **인터페이스를 구현**하고 있어야 사용 가능하다.

### 📌 작동 방식

- 프록시는 인터페이스를 구현한 새로운 클래스를 런타임에 생성하고,
- 메서드 호출을 가로채서 AOP Advice를 적용한 후,
- 다시 원래 메서드를 호출한다.

### 📌 특징

|항목|설명|
|---|---|
|기반|인터페이스|
|구현 방식|Java Reflection API|
|성능|상대적으로 빠름|
|제약|반드시 인터페이스가 있어야 함|

### 📌 예

```java
public interface MemberService {
    void join(String name);
}
```

> 이 경우 Spring은 JDK Dynamic Proxy를 사용할 수 있음.

---

## ✅ 2. CGLIB (Code Generation Library)

### 📌 개념

- **클래스를 상속하여 서브 클래스를 생성**해서 프록시를 만드는 방식.
- 타겟 객체가 **인터페이스가 없어도**, **구체 클래스만 있어도** 동작 가능.

### 📌 작동 방식

- 런타임에 **Bytecode 조작을 통해** 서브 클래스를 만들어 Advice를 적용한다.
- CGLIB은 ASM이라는 라이브러리를 내부적으로 사용하여 바이트코드를 직접 조작한다.

### 📌 특징

|항목|설명|
|---|---|
|기반|클래스 (구현체)|
|구현 방식|바이트코드 조작 (ASM)|
|성능|JDK보다 느릴 수 있음 (클래스 조작 필요)|
|제약|`final` 클래스나 `final` 메서드는 프록시 불가|

### 📌 예

```java
public class MemberService {
    public void join(String name) {
        System.out.println(name + " 가입 완료");
    }
}
```

> 이 경우 Spring은 CGLIB 프록시를 사용하게 됨.

---

## ✅ 두 방식 비교 요약

|비교 항목|JDK Dynamic Proxy|CGLIB Proxy|
|---|---|---|
|사용 조건|인터페이스 필요|구체 클래스 필요|
|구현 방식|java.lang.reflect.Proxy 사용|바이트코드 조작|
|성능|빠름|다소 느릴 수 있음|
|final 클래스|프록시 생성 가능|프록시 생성 불가능 (`final`이면)|
|적용 우선순위|Spring은 먼저 JDK → 없으면 CGLIB 사용||

---

## ✅ Spring AOP에서 어떤 것을 언제 쓰나?

- 기본적으로 Spring은 **JDK Dynamic Proxy를 우선 사용**.
- 만약 인터페이스가 없다면, **자동으로 CGLIB Proxy로 전환된다**.

```java
@Configuration
@EnableAspectJAutoProxy(proxyTargetClass = true)
public class AppConfig {

}

```

- 위와 같이 `proxyTargetClass=true`로 설정하면 **무조건 CGLIB**을 사용하게 된다..
