# Spring boot
- 스프링 프레임워크 기반 프로젝트를 복잡한 설정 없이, 쉽고 빠르게 만들어주는 라이브러리
- 사용자가 일일이 모든 설정을 하지 않아도, 자주 사용되는 기본 설정을 알아서 해줌

## 왜 사용할까?
> 스프링 프레임워크를 사용하려면 많은 XML 설정 파일(`web.xml`, `rootContext.xml`, `ServletContext.xml` 등)들을 작성해야 하고, 설정 방법을 모두 외우지 못했다면 기존에 사용했던 설정을 Copy&Paste 하거나, 개발자가 일일이 인터넷 검색을 통해서 설정해주어야 하는데, 이는 곧 생산성과 비용 문제와 연결된다.
> 
> 하지만,
> Spring boot를 사용하면 복잡한 설정 없이, 쉽고 빠르게 스프링 프레임워크를 사용할 수 있다.(`application.properties` or `application.yml` 제공)
> 
> **`application.properties`**
> key = value
```
spring.web.mvc = 값
spring.web.prefix = ...

server.port = ...
spring.web.suffix = ...
```
>
> **`application.yml`**
> key : value
```
spring:
	web:
		mvc:
		prefix:
		suffix:
server:
	port:
```


## 장점
### 1. 라이브러리 관리의 자동화
- Spring boot 버전을 선택하면, 그 버전 안에서 관련된 라이브러리들이 가장 호환성이 좋은 라이브러리를 관리해준다.
- Spring boot의 Starter 라이브러리를 등록해서, 라이브러리의 의존성을 간단하게 관리할 수 있다.

### 2. 라이브러리 버전 자동 관리
- 기존에는 스프링 라이브러리의 버전을 하나하나 직접 입력해야 했지만, 스프링 부트는 `pom.xml` 에 스프링 부트 버전을 입력하면 스프링 라이브러리 뿐만 아니라, 서드 파티 라이브러리들도 호환되는 버전으로 알아서 다운해준다.

### 3. 설정의 자동화
- 스프링 부트는 `@EnableAutoConfiguration` 어노테이션을 선언해서 스프링에서 자주 사용 했 던 설정들을 알아서 등록해준다.

### 4. 내장 Tomcat
- 스프링 부트는 Tomcat을 내장하고 있기 때문에 `@SpringBootApplication` 어노테이션이 선언되어있는 클래스의 `main()` 메소드를 실행하는 것만으로 서버를 구동시킨다.
- 내장 톰캣을 사용하려면 특별한 설정 없이 Web Starter 의존성만 추가해주면 된다.

### 5. 독립적으로 실행 가능한 JAR
- 웹 프로젝트라면 `WAR` 파일로 패키징 해야하지만 스프링 부트는 내장 톰캣을 지원하기 때문에, `JAR` 파일로 패키징해서 웹 애플리케이션을 실행시킬 수 있다.

# Hikari
### Hikari란?
> > HikariCP(히카리 CP, Hikari Connection Pool)
> → **데이터베이스 커넥션 풀(Connection Pool)** 구현체이다.

- **“CP”** 는 _Connection Pool_의 약자
- **“Hikari(光)”** 는 일본어로 _빛(light)_, 이름 그대로 “가볍고 빠른 커넥션 풀”을 지향한다.
- Java 생태계에서 가장 **빠르고 안정적인 커넥션 풀 구현체**로 평가받고 있다.

### Spring Boot와의 관계
> Spring Boot 2.x 이상에서는 기본 커넥션 풀로 HikariCP를 자동 채택
> (`spring-boot-starter-data-jpa`나 `spring-boot-starter-jdbc` 사용 시 자동 포함)
> 
> 즉, 별도 설정 없이도 내부적으로 다음과 같은 구조가 된다.

```text
Spring Data JPA
   ↓
Hibernate (JPA 구현체)
   ↓
DataSource (HikariDataSource)
   ↓
HikariCP (Connection Pool)
   ↓
Database
```

### Connection Pool이란?
> DB 커넥션은 생성·해제 비용이 큰 리소스이다.
> 따라서 매번 새로 열고 닫는 대신, **미리 일정 개수의 커넥션을 만들어 재사용한다**.
> 이걸 관리하는 게 **Connection Pool이다**.
> HikariCP는 이 풀을 빠르고 효율적으로 관리한다.

### 로그에서 보이는 예시
Spring Boot 애플리케이션 실행 시, 이런 로그가 자주 나온다.

```text
HikariPool-1 - Starting...
HikariPool-1 - Added connection conn0: url=jdbc:h2:mem:testdb user=SA
HikariPool-1 - Start completed.
```

이 의미는 다음과 같다.

|로그 내용|의미|
|---|---|
|`Starting...`|커넥션 풀 생성 중|
|`Added connection conn0`|커넥션(데이터베이스 연결) 생성 완료|
|`Start completed.`|커넥션 풀 초기화 완료|

### HikariCP의 장점
|항목|설명|
|---|---|
|🚀 빠름|최소한의 동기화, 가벼운 코드로 성능 최적화|
|🧠 효율적|메모리, 스레드 리소스 사용이 매우 적음|
|🧩 안정성|JDBC 표준 기반으로 안정적이고 다양한 DB와 호환|
|🔧 설정 간단|대부분 기본 설정으로 충분 (Spring Boot 자동 설정)

### Hikari 설정 커스터마이징 예시
`application.yml` 예시:

```yaml
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/testdb
    username: root
    password: 1234
    driver-class-name: com.mysql.cj.jdbc.Driver
    hikari:
      maximum-pool-size: 10
      minimum-idle: 5
      idle-timeout: 30000       # 30초
      max-lifetime: 600000      # 10분
      connection-timeout: 20000 # 20초

```

이 설정은 DB 연결 수, 유휴 시간, 타임아웃 등을 조정한다.


### HikariCP(히카리 커넥션 풀)의 세부 동작을 제어하는 옵션 설명
#### `maximum-pool-size`
- **의미**: 커넥션 풀에서 동시에 유지할 수 있는 **최대 커넥션 수**
- **설명**:
    애플리케이션이 동시에 여러 요청을 처리할 때, DB에 접근하기 위해 커넥션을 여러 개 사용할 수 있다.
    이 값이 너무 작으면 요청이 몰릴 때 대기 시간이 늘어나고, 너무 크면 DB나 서버 리소스가 낭비될 수 있다.
- **기본값**: 10
- **예시**: `maximum-pool-size: 10` → 동시에 최대 10개의 DB 커넥션을 사용할 수 있음.

#### `minimum-idle`
- **의미**: 풀에서 유지할 **최소 유휴(Idle) 커넥션 수**
- **설명**
    애플리케이션이 한가할 때도, 최소한 이 수만큼의 커넥션은 미리 만들어서 대기 시켜 둔다.
    갑작스러운 트래픽 증가에 대비할 수 있다.
- **주의점**:
    `minimum-idle` 값이 `maximum-pool-size`보다 크면 `maximum-pool-size`로 자동 조정된다.

#### `idle-timeout`
- **의미**: 유휴 상태(사용되지 않는 상태)로 유지할 수 있는 **최대 시간 (밀리초)**
- **설명**:
    커넥션이 `idle-timeout` 이상 사용되지 않으면 풀에서 제거된다.
    단, `minimum-idle` 개수 이하로는 내려가지 않는다.
- **예시**:
    `idle-timeout: 30000` → 30초 동안 사용되지 않은 커넥션은 제거됨.

## 단위 테스트(Unit Test)
### 정의
- 단위 테스트(Unit Test)는 애플리케이션의 가장 작은 단위(주로 메서드 또는 클래스)를 **독립적**으로 테스트하는 것을 말한다.
- 예 : `MemberService.join()` 메서드의 정상 동작 여부를 테스트

### 왜 필요한가?
- **개별 기능의 정확성 보장** : 메서드 하나하나가 원하는 결과를 내는지 검증 가능하다
- **리팩토링 시 안정성 확보** : 코드 변경 후에도 기존 기능이 유지되는지 빠르게 확인 가능하다.
- **디버깅 시간 단축** : 어디서 문제가 발생했는지 빠르게 파악 가능하다
- 애플리케이션을 가동해서 직접 테스트하는 것보다 테스트를 빠르게 진행 할 수 있다.
- 코드가 작성된 목적을 명확하게 표현 할 수 있으며, 불필요한 내용이 추가 되는 것을 방지 할 수 있다.

### 언제 사용하는가?
- 기능을 작성한 **후**, 또는 작성 **전**(테스트 주도 개발, TDD)
- 리팩토링 또는 라이브러리 업그레이드 시

## 테스트 코드를 작성해야 하는 이유
|이유|설명|
|---|---|
|안정성|코드 변경 후에도 기존 기능이 정상 동작하는지 검증 가능|
|문서화|테스트는 코드의 사용 예시와도 같아서 다른 개발자가 참고 가능|
|빠른 회귀 테스트|수동 테스트 없이 빠르게 반복 검증|
|리팩토링 보조|리팩토링 시 기능 손상 여부를 빠르게 확인|
|버그 예방|개발 초기부터 오류를 줄이고 품질을 개선|

## Spring Boot에서 제공하는 테스트의 종류
|종류|설명|
|---|---|
|단위 테스트 (Unit Test)|클래스 또는 메서드 단위 테스트|
|통합 테스트 (Integration Test)|여러 컴포넌트, Bean 간 상호작용 테스트|
|웹 계층 테스트|Controller 계층만 테스트|
|JPA 테스트|Repository와 DB 매핑 테스트|
|Mock 테스트|Bean 대신 가짜 객체(Mock)를 주입|

### 기본 테스트 지원
Spring Boot는 테스트를 위해 다음과 같은 기본 지원을 제공한다.
- `spring-boot-starter-test` 의존성을 추가하면 JUnit, Mockito, Hamcrest, AssertJ 등 여러 테스트 라이브러리가 자동으로 들어간다.
- 기본 테스트 실행 프레임워크로는 JUnit 5 (Jupiter) 가 사용된다.
- Spring Framework/Boot 자체의 테스트 유틸리티(예: `@SpringBootTest`, `@WebMvcTest`, `MockMvc`, `TestRestTemplate` 등)를 제공하여 통합 테스트 및 웹 계층 테스트가 용이하다.

### 주요 애노테이션 및 기능
- `@SpringBootTest`
    - Spring Boot 애플리케이션 컨텍스트 전체를 띄워서 테스트할 수 있음.
    - 예시:

```java
@SpringBootTest
class MyApplicationTests {
    @Test
    void contextLoads() {
    }
}
```

- `@WebMvcTest`
    - 웹 계층(Controller 등)만 부분적으로 띄워서 테스트할 때 사용. Spring MVC 관련 Bean만 주입됨.
- `@DataJpaTest`, `@JdbcTest` 등
    - JPA 계층, 데이터베이스 계층만 집중해서 테스트할 때 사용하는 slicing 테스트 지원.
- MockMvc / TestRestTemplate
    - `MockMvc`: 서버 실제 실행 없이 웹 요청/응답 계층을 테스트할 수 있도록 제공됨.
    - `TestRestTemplate`: 통합 테스트 중 실제 HTTP 요청을 통해 애플리케이션을 띄우고 검증할 때 사용됨.

### 사용 시 장·단점 및 팁
- **장점**
    - 설정이 간편 : 기본 스타터(`spring-boot-starter-test`)만 추가하면 여러 테스트 라이브러리를 바로 사용 가능.
    - 계층별 테스트(웹·데이터·통합) 지원이 잘 돼 있어 단위 테스트 vs 통합 테스트 비교하기 좋음.

- **단점 / 주의사항**
    - `@SpringBootTest` 같이 전체 컨텍스트를 띄우는 테스트는 실행 속도가 느릴 수 있고, 자주 사용하면 테스트 유지보수가 힘들어질 수 있음.
    - slicing 방식(`@WebMvcTest`, `@DataJpaTest` 등)을 잘 활용해서 **필요한 범위만 로드하는 테스트 설계**가 중요함.

## JUnit과 Assertion(Assert or Assertions)의 관계
### JUnit이란?
- **자바 기반 단위 테스트 프레임워크**
- Spring Boot는 기본적으로 JUnit 5 (Jupiter)를 사용

### Assertion이란?
- **테스트 결과를 검증하는 메서드들**
- JUnit에 포함되어 있으며, 조건이 맞지 않으면 테스트를 실패 처리
- **검증 도구**로는 버전에 따라 `Assertions`와 `Assert` 있다.

### 관계:
- `JUnit`은 테스트 환경과 실행을 제공
- `Assert`는 테스트의 성공/실패 여부를 판단하는 **검증 도구**


## 🔸 Assert 와 Assertions차이점
|   |   |   |
|---|---|---|
|항목|`Assert`|`Assertions`|
|소속|`org.junit.Assert`|`org.junit.jupiter.api.Assertions`|
|JUnit 버전|JUnit 4|JUnit 5 (Jupiter)|
|사용 방식|메서드에 `@Test`를 붙여 실행|메서드에 `@Test`를 붙여 실행 (JUnit 5 Jupiter 기반)|
|예시 메서드|`Assert.assertEquals(...)`|`Assertions.assertEquals(...)`|
|클래스 이름|`Assert` 클래스 이름 자체가 짧음|`Assertions` 이름이 명확히 복수형

### 예시
```java
@Test
void testSum() {
	int result = 2 + 3;
	Assertions.assertEquals(5, result); // Assert가 결과를 검증
}
```

### 예제
```java
@Test
@DisplayName("두 수의 합 테스트")
void testSum() {
	assertEquals(5, 2+3);
}

@BeforeEach
void setUp() {
	System.out.println("각 테스트 전에 실행됩니다.");
}
```

### JUnit 5 애노테이션
|애노테이션|적용 대상|설명|
|---|---|---|
|`@Test`|메서드|해당 메서드를 테스트 메서드로 지정|
|`@BeforeEach`|메서드|각 테스트 실행 **전**에 실행 (초기화 작업 등)|
|`@AfterEach`|메서드|각 테스트 실행 **후**에 실행 (리소스 정리 등)|
|`@BeforeAll`|메서드 (static)|**모든 테스트 시작 전** 1회 실행 (전역 설정 등)|
|`@AfterAll`|메서드 (static)|**모든 테스트 완료 후** 1회 실행|
|`@DisplayName`|클래스, 메서드|테스트 이름을 사람이 읽기 쉬운 형태로 지정|
|`@Disabled`|클래스, 메서드|해당 테스트를 **비활성화**하여 실행하지 않음|
|`@Nested`|클래스|내부 클래스를 계층적 테스트 그룹으로 구성|
|`@Tag`|클래스, 메서드|테스트 그룹을 태깅 (ex. @Tag("slow"))|
|`@RepeatedTest(value)`|메서드|테스트를 지정한 횟수만큼 반복 실행|
|`@ParameterizedTest`|메서드|다양한 인자값을 주입하여 테스트 반복 실행|

## Assertions 주요 메서드 정리
|메서드|설명|
|---|---|
|`assertEquals(expected, actual)`|예상값과 실제값이 같은지 비교|
|`assertNotEquals(expected, actual)`|두 값이 다르면 성공|
|`assertTrue(condition)`|조건이 true면 성공|
|`assertFalse(condition)`|조건이 false면 성공|
|`assertNull(object)`|객체가 null인지 검사|
|`assertNotNull(object)`|객체가 null이 아닌지 검사|
|`assertThrows(Exception.class, () -> {})`|특정 예외 발생 여부 검사|
|`assertAll(...)`|여러 테스트를 한번에 실행하여 모두 실패 여부 확인|
|`assertTimeout(Duration.ofMillis(1000), () -> {})`|실행 시간 제한 테스트|
