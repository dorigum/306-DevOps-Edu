### ChatClient API
[![](https://docs.spring.io/spring-ai/reference/_/img/favicon.ico)Chat Client API :: Spring AI Reference](https://docs.spring.io/spring-ai/reference/api/chatclient.html)​

- **ChatClient** API는 LLM(Large Language Models)과의 상호작용을 추상화하여, 개발자가 복잡한 API 호출 로직을 직접 구현하지 않고도 선언 적인 방식으로 AI 기능을 구축할 수 있게 돕는다.
- **ChatClient**는 Spring AI에서 AI 모델과 대화하기 위한 **Fluent API(유동적 API)** 스타일의 클라이언트이다.
- **ChatClient**는 프롬프트 템플릿 구성, 상태 관리, 데이터 변환(Output Parsing) 등을 하나의 체인으로 묶어 처리한다.
- **ChatClient**는 단순한 질의응답을 넘어 다양한 에이전틱(Agentic) 워크플로우에 활용된다.

#### 특징
- **Fluent Interface:** `.prompt()`, `.user()`, `.call()` 등 메서드 체이닝을 통해 가독성 높은 코드를 작성할 수 있다.

- **Infrastructure Agnostic:** 기반 모델(Gemini, GPT 등)을 교체하더라도 비즈니스 로직 수정이 최소화된다.

- **Advisors:** 로깅, 토큰 측정, RAG(Retrieval-Augmented Generation)를 위한 컨텍스트 추가 등을 인터셉터 방식으로 삽입할 수 있다.

### AI Agent
#### 자동화 툴에서 AI 활용 방법
![[Pasted image 20260612110608.png]]

>위 그림은 **AI를 활용한 자동화**와 **AI Agent를 활용한 자동화**의 차이를 비교한 내용이다.
>
>왼쪽은 일반적인 AI 자동화 방식이다.
>미리 정해진 순서대로 업무를 실행하는 과정에 AI를 하나의 기능으로 활용하는 구조이다.
>
>**예를 들어**, 구글 드라이브에서 PDF 파일을 읽고 → Gemini가 내용을 요약한 뒤 → 요약 결과를 이메일로 전송하는 흐름이다.
>업무 순서가 고정되어 있기 때문에 어떤 작업이 어떻게 수행되는지 예측하기 쉽고 안정적이라는 장점이 있다.
>
>**반면**, 새로운 요청이 들어오거나 상황에 따라 다른 처리가 필요하면 워크플로우를 직접 수정해야 하므로 유연성이 떨어질 수 있다.
>
>
>오른쪽은 AI Agent 기반 자동화 방식이다.
>AI Agent는 단순히 지시 받은 작업을 수행하는 것이 아니라, **사용자의 요청을 이해하고 어떤 작업이 필요한지 스스로 판단한다.**
>
>예를 들어 사용자가
>**"지난주 프로젝트 진행 상황을 정리해서 팀원들에게 메일로 보내줘**"
>라고 요청하면,
>AI Agent는 먼저 필요한 정보를 찾고, 내용을 정리한 뒤, 이메일 전송 도구를 선택하여 결과를 전달한다.
>즉, 사람이 일하는 것처럼 **생각 → 판단 → 도구 선택 → 실행** 과정을 수행하는 것이다.
>
>그림 아래를 보면 차이가 더 명확하다.
>왼쪽은 Chat → LLM → Gmail 순서로 고정된 흐름을 가지고 있다.
>
>반면 오른쪽 AI Agent는 LLM뿐만 아니라 메모리(Memory), 다양한 Tool을 연결하여 상황에 맞게 활용한다.
>
>그래서 같은 Agent라도 어떤 요청이 들어오느냐에 따라 이메일을 보낼 수도 있고, 문서를 검색할 수도 있으며, 외부 API를 호출할 수도 있다.
>
>정리하면,
>**AI 자동화는 "정해진 절차를 자동화하는 것"** 이고,
>**AI Agent 자동화는 "목표를 주면 스스로 방법을 결정하여 실행하는 것"** 이다.
>
>그리고 최근 Spring AI, LangChain, OpenAI Agent, MCP 같은 기술들이 등장하면서 단순 자동화를 넘어 AI Agent 기반 시스템 구축이 점점 중요해지고 있다.

### AI Agent 개요
데이터를 수신하고 **합리적인 결정을 내리며 특정 목표를 달성하기 위해 환경 내에서 행동하는 자율 시스템**

[https://blog.n8n.io/ai-agents/](https://blog.n8n.io/ai-agents/)
[https://aws.amazon.com/what-is/ai-agents/](https://aws.amazon.com/what-is/ai-agents/)

![[Pasted image 20260612111145.png]]

AI Agent는 주변 환경으로부터 정보를 수집하고(Sensors), 이를 LLM과 프롬프트를 통해 분석하여 판단한다.

수집된 정보는 Agent 내부에서 처리되어 목표를 달성하기 위한 최적의 행동이 **결정**된다.

이후 Actuators를 통해 이메일 전송, 데이터 조회, API 호출과 같은 실제 작업을 **수행**한다.

즉, **AI Agent는 단순히 답변을 생성하는 것이 아니라 환경을 이해하고 스스로 판단하여 행동하는 자율 시스템이다.**

Spring AI에서는 이러한 Agent 개념을 기반으로 LLM, Memory, Tool을 결합하여 다양한 업무를 자동화할 수 있다.

#### 핵심 구성 요소
- Model : 에이전트의 두뇌 역할을 하는 LLM (예: Gemini 1.5 Pro, GPT-4o).
- Tools : 에이전트가 사용할 수 있는 '손과 발' (예: Google Sheets 연동, Slack 전송, MCP 서버 호출, 웹 검색).
- Memory : 과거의 대화 내용을 기억하여 맥락 있는 답변을 가능하게 함.

## Spring AI Advisor

> **💡Spring AI의 Advisor는 ChatClient 요청과 응답 사이에 끼어드는 인터셉터**
> 즉, 사용자의 질문이 LLM으로 전달되기 전에 내용을 보강하거나, LLM 응답이 반환된 후 후처리할 수 있다. 공식 문서에서도 Advisor는 요청·응답을 관찰하거나 보강하는 용도로 설명한다.

#### AI를 위한 Interceptor

- Spring Web의 Interceptor 개념을 완벽히 계승했다.
- 애플리케이션과 LLM 사이의 요청/응답 흐름을 가로채서(Intercept) 전처리와 후처리를 수행한다.
- **전처리 작업**은 주로 프롬프트에 컨텍스트(Context, 문맥)를 추가하는 과정을 의미한다.
- ==**컨텍스트란**== LLM의 응답 정확도를 높이기 위해 함께 제공되는 정보로 “로컬 데이터, 이전 대화 내용, 현재 상황을 설명하는 텍스트”등이 될 수 있다.
- 후처리 작업은 주로 **LLM의 응답을 검사하고, 애플리케이션이 요구하는 형식으로 변환하는 과정을 의미**한다.
- 또한, 사용자의 질문과 LLM의 응답을 함께 데이터베이스나 벡터 저장소에 기록하여 이후 검색이나 문맥 유지에 활용할 수도 있다.
- 프롬프트를 강화하는 전처리와 응답을 파싱하는 후처리 로직을 캡슐화하여, 재사용 가능하고 유지보수가 용이한 모듈식 AI 파이프라인을 구축할 수 있다.

`MyLoggingAdvisor .java`

```java
public class MyLoggingAdvisor implements CallAdvisor {
	private static final Logger log = LoggerFactory.getLogger(MyLoggingAdvisor.class);
	
	@Override
	public ChatClientResponse adviseCall(ChatClientRequest chatClientRequest, CallAdvisorChain callAdvisorChain) {
		// 전처리
		log.info("ChatClientRequest: {}", chatClientRequest);
		// LLM 호출
		var chatClientResponse = callAdvisorChain.nextCall(chatClientRequest);
		// 후처리
		log.info("ChatClientResponse: {}", chatClientResponse);
		return chatClientResponse;
	}
	// Advisor는 자신이 갖고 있는 Order 번호를 기준으로 오름차순으로 실행됩니다.
	@Override
	public int getOrder() {
		return 100;
	}
	
	@Override
	public String getName() {
		return this.getClass().getSimpleName();
	}
}
```

>💡**CallAdvisorChain 이란?**
>`CallAdvisorChain`은 여러 Advisor를 순서대로 실행하기 위한 체인 객체이다.


`AppConfig.java`

```java
@Bean
public ChatClient chatClient(ChatClient.Builder chatClientBuilder){
		return chatClientBuilder
		.defaultSystem(resource)
		.defaultAdvisors(new MyLoggingAdvisor())
		.build();
}
```

### Shared Context
>Shared Context는 Spring AI Advisor 체인에서 요청(Request)과 응답(Response) 처리 과정 동안 여러 Advisor가 데이터를 공유할 수 있도록 제공하는 공용 저장소(`Map<String, Object>`)로 데이터 흐름과 상태를 공유한다.

![[Pasted image 20260612120912.png]]

>사용자의 요청이 `ChatClientRequest`로 생성되면 Prompt와 함께 공통 Context 영역에 접근할 수 있다.
>이 Context는 `Map<String, Object>` 형태로 구성되어 있으며, **Advisor 간에 데이터를 공유하는 저장소 역할**을 한다.
>각 Advisor는 요청 처리 과정에서 필요한 정보를 Context에 저장할 수 있고, 이후 실행되는 다른 Advisor나 응답 처리 단계에서 해당 데이터를 다시 사용할 수 있다.
>LLM 호출이 완료되면 `ChatClientResponse` 역시 동일한 Context를 참조하여 이전 단계에서 저장된 상태 정보나 처리 결과를 활용할 수 있다.
>즉, Shared Context는 **Advisor 간 데이터 전달과 상태 공유를 위한 공용 메모리 공간**이며, 대화 ID, 사용자 정보, RAG 검색 결과, 토큰 사용량 등의 데이터를 저장하고 공유하는 데 사용된다.

#### 데이터 흐름과 상태 공유
- 런타임에 `Advisor`의 동작을 변경할 수 있는 유연성이 필요한 경우 사용
    - 각 체인을 통과하는 핵심 레코드인 `ChatClientRequest`와 `ChatClientResponse` 는 완전히 다른 구조를 갖지만 전체 `Advisor Chain`에서 공유해야 할 데이터를 위해 하나의 공통된 컨테이너인 `Map(String, Object)` 타입의 context를 가지고 있다.
    
- `ChatClient`가 실행될 때 `Advisor`와 공유해야 할 데이터가 있다면 디음 코드로 키와 값을 제공할 수 있다.

- 각 Advisor는 ChatClientRequest 또는 ChatClientResponse 레코드의 context() 메소드를 통해 공유 데이터인 `Map(String, Object)`를 얻고, 여 기에 저장된 값을 읽고 활용할 수 있다.

### 참고) Re-Reading (재독해) 추론 기법
![[Pasted image 20260612122236.png]]

Re-Reading은 사람이 시험 문제를 풀 때 문제를 한 번 더 읽어 핵심 조건을 확인하듯이, AI도 질문을 다시 읽도록 유도하여 추론 정확도를 높이는 기법이다.

일반적인 LLM은 긴 문장을 읽는 과정에서 중요한 조건을 놓칠 수 있는데, Re-Reading은 질문이나 핵심 조건을 한 번 더 강조하여 모델이 중요한 정보를 잊지 않도록 도와준다.

특히 긴 계약서 분석, 번역, 코드 리뷰처럼 문맥 이해가 중요한 작업에서 효과적이며, Spring AI에서는 **ReReadingAdvisor**를 통해 쉽게 적용할 수 있다.

### BaseAdvisor

![[Pasted image 20260612122616.png]]

BaseAdvisor는 AI 요청과 응답 처리 과정에 공통 기능을 추가하기 위해 제공되는 **추상 클래스(Abstract Class)** 이다. 쉽게 말해 ChatClient와 LLM 사이에서 동작하는 **AI 통신용 미들웨어 계층**이라고 생각하면 된다.

개발자는 Advisor 인터페이스의 모든 메서드를 직접 구현할 필요 없이 BaseAdvisor를 상속받아 필요한 부분만 오버라이드하여 사용할 수 있습니다. 이를 통해 중복 코드를 줄이고 AI 파이프라인을 보다 쉽게 확장할 수 있다

BaseAdvisor는 크게 두 단계로 동작한다. 먼저 `before()` 메서드는 AI 모델 호출 직전에 실행되며 프롬프트 수정, 컨텍스트 주입, RAG 데이터 추가, Re-Reading 지시문 삽입 등의 작업을 수행한다. 이후 AI가 응답을 반환하면 `after()` 메서드가 실행되어 응답 검증, 데이터 포맷 변환, 유해성 필터링, 로깅 및 모니터링과 같은 후처리를 수행한다.

따라서 BaseAdvisor를 사용하면 AI 요청 전처리와 응답 후처리를 표준화할 수 있으며, 다양한 AI 기능을 모듈처럼 조합하여 사용할 수 있다.

### Spring AI Built-in Advisor 정리

Spring AI의 Advisor는 **ChatClient와 LLM 사이에서 요청(Request)과 응답(Response)을 가로채어 처리하는 인터셉터(Interceptor) 역할**을 한다.

즉, 개발자가 직접 프롬프트를 조작하지 않아도 공통 기능을 자동으로 추가할 수 있도록 해주는 확장 포인트이다.

**Advisor란?**

```TEXT
사용자 질문
      ↓
  Advisor
      ↓
     LLM
      ↓
  Advisor
      ↓
사용자 응답
```

Advisor는

- 요청 전처리(Before)
- 응답 후처리(After)

를 담당한다.

**Spring AI는 기업 환경에서 자주 사용하는 기능들을 Built-in Advisor 형태로 제공한다.**

### Spring AI Built-in Advisor 4대 유형

```text
1. Logging
2. Safeguard
3. Memory
4. RAG
```

##### 개요

- 대표 구현체: `SimpleLoggerAdvisor`
