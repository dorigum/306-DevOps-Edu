# 고가용성(High Availability, HA)
- **정의**
	- 시스템이 장애가 나더라도 서비스가 가능한 한 중단되지 않고 계속 동작할 수 있도록 하는 성질

- **목표**
	- 서비스 다운타임 최소화
	- 장애 발생 시 자동 복구(Failover)
	- 이중화(Replication, Clustering) 등을 통한 안정성 확보

- **예시**
	- DB 서버를 한 대만 두면 그 서버가 다운되면 서비스 전체가 멈춤
	- 따라서 여러 대(DB Cluster)를 두고, 한 대가 죽으면 다른 대가 즉시 대신 동작하도록 구성.
		- 즉, **"항상 켜져 있는 서비스"** 를 만들기 위한 전략이다.


---
## ✅트레이드 오프(Trade-off, 상충관계)

- **정의**
	- ==하나를 얻기 위해 다른 하나를 희생해야 하는, 양립할 수 없는 선택 상황==을 의미(어떤 장점을 얻으려면 다른 부분에서 손해를 감수해야 하는 상황)
	- 효율이나 성능을 높이면 비용이나 품질이 낮아지는 식의 이율배반적 관계
	- 자원이 제한된 상황에서 **최적의 균형(Trade-off)을 찾는 의사 결정의 핵심 개념

- 시스템 설계에서는 성능, 비용, 안정성, 확장성, 일관성 같은 요소들 사이에서 균형을 잡아야 함

- **예시**
    - 고가용성을 위해 DB를 여러 대 두면 **안정성은 올라가지만 비용이 증가**함.
    - DB 복제를 하면 **읽기 성능은 좋아지지만, 일관성(Consistency)이 늦어질 수 있음**.
    - 분산 시스템에서 유명한 **CAP 이론**도 결국 "Consistency, Availability, Partition tolerance 중 두 개만 확실히 보장 가능하다"는 **trade-off**를 설명하는 개념

- **핵심 특징 및 사례**
	- **경제/정책:** 실업률을 낮추면 물가가 상승하는 필립스 곡선 관계
	- **비즈니스:** 원가 절감(비용)을 위해 품질(서비스)을 낮추는 경우
	- **엔지니어링/IT:** 시스템의 성능(속도)을 높이기 위해 용량(저장 공간)을 희생하거나, 보안을 강화하면 편리함이 감소하는 경우
	- **머신러닝:** 편향(Bias)을 낮추면 분산(Variance)이 증가하는 데이터 모델의 상충 관계

- **정리**
	- **고가용성** = 서비스 중단 없이 계속 동작하도록 만드는 것
	- **Trade-off** = 어떤 걸 강화하면 다른 걸 희생해야 하는 균형 문제

👉 예를 들어, "고가용성을 위해 DB 이중화를 할까?" 라고 하면, 그 순간 **비용 및 복잡성이 늘어난다는 trade-off**를 감수해야 한다는 뜻

## CAP 이론(CAP Theorem)
>분산 시스템에서는
>**Consistency, Availability, Partition Tolerance**
>이 세 가지를 동시에 완벽하게 보장할 수 없다.

이 이론은 2000년 **Eric Brewer**가 제안했고, 이후 정식 증명되었다.

💡트레이드오프는 일반적인 개념이고,
CAP 이론은 **분산 시스템에서 발생하는 대표적인 트레이드오프 사례**이다.

---
#### CAP의 3가지 요소
1. **Consistency (일관성)**
	- 예:
		- A 서버에 100원 저장
		- B 서버에서도 즉시 100원으로 보여야 함
즉,
👉 **항상 최신 데이터 보장**

2. **Availability (가용성)**
- 모든 요청에 대해 항상 응답을 반환한다.
	- 예:
		- 서버 일부가 죽어
		- 사용자는 계속 서비스 이용 가능
즉,
👉 **에러 대신 반드시 응답**

3. **Partition Tolerance (분할 허용성)**
- 네트워크가 끊겨도 시스템이 동작해야 한다.
	- 예:
		- 서버 A ↔ 서버 B 통신 단절
		- 그래도 각각은 살아있어야 함

즉,
👉 **네트워크 장애를 견딘다.**

---
### 핵심: 왜 세 개를 다 못 지키는가?

**가정**
서버 A와 B가 있음
그런데 네트워크가 끊겼다 (Partition 발생)
이제 선택해야 한다.

**🎯 선택 1 — Consistency를 지킨다.**
- A가 데이터 변경
- B와 통신 안 됨
- 최신 데이터 보장 불가
	👉 요청을 거절해야 함
	✔ Consistency 유지
	❌ Availability 포기

**🎯 선택 2 — Availability를 지킨다**
- A와 B가 각각 요청 처리
- 서로 데이터 다를 수 있음
	✔ Availability 유지
	❌ Consistency 깨짐

💡즉,
**CAP = C + A + P**
But 현실에서는 P는 반드시 발생함
→ 결국 C와 A 중 하나를 선택
그래서 =="세 개 중 두 개만 확실히 보장 가능하다"== 라는 말이 나오는 것

---
### 📌 실무에서는 어떻게 될까?
| 시스템 유형      | 선택                   |
| ----------- | -------------------- |
| 금융 시스템      | CP (일관성 + 분할허용성)     |
| SNS, 캐시 시스템 | AP (가용성 + 분할허용성)     |
| 단일 서버 DB    | CA (Partition 없음 가정) |

#### 비유로 이해하기
##### 📞 전화 통화 상황
두 사람이 전화 중인데 > 네트워크 끊김 (Partition)

선택:
1. "다시 연결될 때까지 아무 말도 안 한다" → Consistency
2. "각자 말 계속 한다" → Availability

❌둘 다 동시에 완벽히 유지 불가

#### 중요한 오해 하나
- CAP 이론은 "항상 2개만 선택한다" 는 말이 아니라, 정확히는 ==**Partition이 발생했을 때 C와 A를 동시에 보장할 수 없다**==는 뜻이다.
- 현실에서는 네트워크 장애는 반드시 발생하므로, 결국 C 또는 A를 선택하는 구조가 된다.

#### ✔한 줄 요약
**CAP 이론은** 분산 시스템에서 네트워크 장애가 발생하면 **데이터 정확성(Consistency)** 과 **항상 응답(Availability)** 중 하나를 선택해야 한다는 **트레이드오프 원리**이다.

### useRef
- `useRef`는 React에서 값을 참조하거나 DOM 요소에 직접 접근할 수 있도록 해주는 훅이다.
- `useRef`는 렌더링 사이에 값을 유지할 수 있는 방법을 제공하며,
- 컴포넌트의 렌더링과 관계없이 값이 유지되므로, 렌더링을 유발하지 않기 때문에 성능 상 이점이 있다.

**사용법**
```jsx
const ref = useRef(initialValue);
```

- **initialValue** : useRef로 생성할 참조의 초기 값이다.
	- initialValue는 기본값이 될 수 있으며, DOM 요소를 참조하는 경우에는 null로 초기화하는 경우가 많다.
	- `useRef` 는 `{ current : T }` 형태의 객체를 반환한다.
		- `T`는 `useRef`에 전달한 initialValue의 타입이고 `ref.current`를 통해 값을 읽거나 수정할 수 있다.

## **단방향 데이터 흐름(One-way Data Flow)** 원칙

> 자식 컴포넌트는 props를 “읽기만” 할 수 있고 직접 수정할 수 없다.
> 즉, 자식은 이렇게 하면 안 된다.

```jsx
props.value = 10;  // ❌ 불가능! 오류
```

React에서는 props를 **읽기 전용(read-only)** 으로 취급한다.


---
### 왜 props를 수정할 수 없게 했을까? (중요한 React 철학)

### ▶ 이유 1: **단방향 데이터 흐름(One-way Flow)**

- React에서는 “데이터는 부모 → 자식 방향으로만 흐른다.”
- 만약 자식이 props를 마음대로 바꿀 수 있다면:
	- 상태 흐름이 꼬이고
	- 디버깅이 매우 어려워지고
	- React의 재렌더링 구조가 깨진다

👉그래서 React는 props를 **불변(immutable)** 으로 한다.


---
### props는 불변(immutable)

즉, 아래는 절대 불가능:

```jsx
props.count++;       // ❌
props.name = "John"; // ❌
```


---
### 그렇다면 자식이 부모의 값을 바꾸고 싶으면?

직접 수정은 불가능하지만 → **부모에게 “수정 요청”을 보내는 방식이 정석**이다.

#### ✔ 부모가 setter 함수를 props로 내려주고

```jsx
function Parent() {
  const [count, setCount] = useState(0);

  return <Child count={count} setCount={setCount} />;
}
```

#### ✔ 자식은 props로 받은 함수를 호출한다

```jsx
function Child({ count, setCount }) {
  return (
    <button onClick={() => setCount(count + 1)}>
      증가
    </button>
  );
}
```

##### → 이렇게 “부모의 상태를 변경하는” 것은 가능

##### → 하지만 “props 자체를 수정하는 것”은 절대 불가능

## 정리

|구문|가능 여부|이유|
|---|---|---|
|`props.value = 10`|❌ 불가능|props는 읽기 전용|
|`props.setValue(10)` 같이 부모가 준 함수 호출|⭕ 가능|부모에게 변경 요청|
|자식이 state를 들고 있다가 부모로 전달|⭕ 가능|상태 전달은 props 이용|
> 자식 컴포넌트는 props를 수정할 수 없다. 하지만 “부모가 내려준 함수(props)”를 호출하여 부모 state를 변경할 수는 있다.

### useReducer
- React의 `useReducer()` 는 React의 상태 관리 훅 중 하나로, 복잡한 상태 로직을 처리하거나 여러 값이 연관된 상태를 다룰 때 유용하다.
- `useState`는 상태를 간단하게 관리하는 데 적합하지만, 상태가 복잡하거나 여러 개의 상태가 서로 의존하는 경우 `useReducer`가 더 적합할 수 있다.
- 컴포넌트 내부에 새로운 State를 생성하는 Reat Hook으로 모든 `useState`는 `useReducer`로 대체가 가능하다.
- `useReducer`는 상태 관리 코드를 컴포넌트 외부로 분리 할 수 있다

- **장점**
	- **복잡한 상태 관리**
		- 상태가 복잡하거나 여러 개의 값이 연관된 경우 useReducer는 상태 업데이트를 더 예측 가능하고 깔끔하게 관리할 수 있게 도와준다.

	- **다양한 액션 처리**
		- 리듀서 함수에서 다양한 액션 타입을 처리할 수 있어, 복잡한 상태 변경 로직을 하나의 함수로 통합하여 관리할 수 있다.

	- **읽기 쉬운 코드**
		- 상태를 직접적으로 수정하는 것보다, 상태 업데이트가 항상 명확한 액션을 통해 이루어지기 때문에 코드가 더 읽기 쉽고 유지보수가 용이하다.

	- **디버깅에 유리**
		- 상태 업데이트 로직이 명확한 액션을 통해 이루어지기 때문에, 디버깅이 용이하고 DevTools 같은 툴을 이용한 상태 추적도 가능하다.

## 최적화(Optimization)
> 웹 서비스의 성능을 개선하는 모든 행위를 말한다.

1. 일반적인 웹 서비스 최적화
	- 이미지, 폰트, 코드 파일 등의 정적 파일 로딩 개선
	- 불필요한 네트워크 요청 줄임

2. React App 내부의 최적화
	- 컴포넌트 내부의 불필요한 연산 방지
	- 컴포넌트 내부의 불필요한 함수 재생성 방지
	- 컴포넌트의 불필요한 리렌더링 방지


### useMemo / memo
>React에서 useMemo() 와 memo() 는 모두 불필요한 연산이나 렌더링을 방지하여 성능을 최적화하기 위한 도구이지만, 용도와 사용하는 위치가 다르다.

#### 1. useMemo() : 값(결과)를 Memoization
**개념**
- useMemo의 Memo는 Memoization(메모이제이션)을 의미
- 기존에 수행한 연산의 결과 값을 어딘가에 저장해 두고 동일한 입력이 들어오면 저장해둔 값을 재활용하는 프로그래밍 기법이다. (캐싱기법)
- **컴포넌트 내부**에서 연산의 결과를 저장해두고, 의존성이 바뀌지 않으면 **이전 결과를 재사용**
- `useEffect` 처럼 **의존성 배열**을 사용해서 특정 값이 바뀔 때만 연산을 다시 실행

**사용 예시**
```jsx
import { useMemo } from 'react';

const ExpensiveComponent = ({ number }) => {
	const squared = useMemo(() => {
		console.log("계산 중...");
		return number * number;
	}, [number]);
	
	return <div>{ squared }</div>
};
```
👉 `number` 가 변경되지 않으면, `squared` 는 다시 계산되지 않고 이전 결과가 재사용됨

**사용 시점**
- 복잡하거나 무거운 연산을 수행할 때
	- 정렬, 필터링, 계산 등
- 계산된 값을 리렌더링마다 다시 만들지 않게 하려는 경우


#### 2. memo() : 컴포넌트 자체를 Memoization
**개념**
- 함수형 컴포넌트 전체를 감싸서 props가 바뀌지 않으면 다시 렌더링하지 않음
- `React.memo()` 는 고차 컴포넌트(HOC)로 작동함

**사용 예시**
```jsx
import React from 'react';

const Child = ({ name }) => {
	console.log("Child 렌더링");
	return <div>Hello, { name }</div>
};

export default React.memo(Child);
```
👉 `name` props가 바뀌지 않으면, 부모가 리렌더링 되더라도 `Child` 는 리렌더링되지 않음

**사용 시점**
- 부모 컴포넌트가 자주 렌더링되지만 자식 컴포넌트의 props가 변하지 않을 때
- **불필요한 자식 렌더링을 방지**하고자 할 때

| 항목         | `useMemo()`           | `React.memo()`                  |
| ---------- | --------------------- | ------------------------------- |
| 대상         | 함수의 **결과 값**          | 함수형 **컴포넌트**                    |
| 사용 위치      | **컴포넌트 내부**           | **컴포넌트 외부(정의 시)**               |
| 의존성 기준     | 의존성 배열`([deps])` 로 판단 | props 비교(`shallow compare`) 기준  |
| 주로 사용하는 경우 | 복잡한 계산 결과를 캐시하고 싶을 때  | props가 바뀌지 않고 리렌더링이 되는 상황을 막을 때 |
| 성능 최적화 대상  | 계산 비용                 | 렌더링 비용                          |

#### 💡 결론 -> 언제, 어떤 걸 쓸까?
- **계산이 무거운 연산**이면 ➡ `useMemo()`
- **컴포넌트 리렌더링을 줄이고 싶으면** ➡ `React.memo()`
- **둘 다 함께 사용 가능**
	- `React.memo()` 로 컴포넌트를 감싸고, 그 안에서 `useMemo()` 로 값 캐싱

#### 고차 컴포넌트(HOC) 란?
>*"컴포넌트를 인자로 받아서 새로운 컴포넌트를 반환하는 함수"*
>즉, **컴포넌트를 장식하거나 확장하는 함수**
>
>**함수형 프로그래밍에서 유래된 개념**
>	이 개념은 고차 함수(Higher Order Function)에서 왔다.
>	고차 함수는 **함수를 인자로 받거나 함수를 반환하는 함수**이다.
>	**React에서는** 이 개념을 컴포넌트에 적용해서 **컴포넌트를 인자로 받아 새로운 컴포넌트를 반환하는 함수**를 **고차 컴포넌트(HOC)**라고 부른다.

**대표적인 예시: `React.memo()`**
```jsx
const MyComponent = (props) => {
	return <div>{props.name}</div>;
};

export default React.memo(MyComponent);
```

🔹여기서 `React.memo()` 는 `MyComponent` 를 인자로 받아서, props가 바뀌지 않으면 리렌더링 하지 않는 새 컴포넌트를 만들어서 반환한다.
이처럼 **컴포넌트를 감싸는 함수**는 **HOC**이다.


#### React.memo()를 이용한 최적화
- `React.memo()`는 React 에서 고차 컴포넌트(Higher-Order Component, HOC)로, 컴포넌트의 렌더링 성능을 최적화하는 데 사용된다.
- 주로 컴포넌트가 같은 props로 반복 렌더링될 때 불필요한 렌더링을 방지하기 위해 사용된다.
- `React.memo()`는 컴포넌트를 감싸는 함수로, 이 함수는 컴포넌트가 렌더링될 때 전달되는 props가 **이전 props와 다를 경우**에만 컴포넌트를 재렌더링한다.
- 즉, props가 변하지 않으면 이전에 렌더링한 결과를 재사용하여 렌더링 성능을 최적화한다.

### useCallback
- `useCallback()`은 React 훅(Hook) 중 하나로, 주로 함수 컴포넌트 내에서 함수의 참조를 메모이제이션 (memoization)하는 데 사용된다.
- 즉, 동일한 **의존성 배열**이 주어졌을 때, ==**불필요한 함수 재생성**을 방지하고 기존의 함수 참조를 재사용할 수 있게 도와준다.== 이를 통해 성능 최적화를 유도할 수 있다.
- `useCallback()`은 주로 자식 컴포넌트에 함수를 props로 전달할 때, 불필요하게 매번 새로운 함수가 생성되는 문제를 해결하기 위해 사용된다.

**사용법**
```jsx
import { useCallback } from 'react';

const handleFun = useCallback(콜백함수, [의존성배열])
```

**`useCallback()` 의 2개의 인자**
- **콜백 함수**: 메모이제이션할 함수
- **의존성 배열**: 이 배열 안의 값들이 변경될 때만 콜백 함수가 새로 생성

#### ⚠최적화는
- 최적화가 꼭 필요할 것 같은 연산이나 함수들에게만 선택적으로 적용하는 것이 좋다.
- 최적화에 관련된 함수 또한 최적화를 위한 연산이나 기억 해 두어야 하는 작업들이 필요하다.
- 단순한 작업을 위해 최적화 함수를 사용하면, 오히려 더 많은 연산과 메모리를 차지할 수 있다.
- **최적화는 기능을 완성 한 후에 최적화를 적용하는 것이 좋다.**
